## 通過條件（給人看之前）

每個方向截圖後自己先檢查，結果寫進方向稿說明。不過的先改，不拿去給人挑。

1. **第一眼測試**：用一句話寫出「第一眼看到＿＿，第一步按＿＿」。寫不出來，或有兩個以上的答案，不合格。
2. **第一屏可操作元素數**：`screenshot.mjs` 會回報桌機與手機第一屏各有幾個。有原型時，把原型的同一頁也截一次，寫出兩邊的數字與增減原因；比原型多要說明為什麼。沒有原型時，方向之間互比。這個數字不是越少越好：要和「第一屏看得到多少主要內容」一起看（內容裡的連結進了第一屏，數字會上升）；原型在某個尺寸破版時，那個尺寸的數字不拿來比。
3. **符合分層表**：「一直在」的項目不多於分層表；可以收得更深，不能往上提。收起來的東西都有看得到、寫明內容的入口。行銷頁改對照第 3 步寫的首屏一句話、主要行動與區塊順序。
4. **方向之間資訊安排不同**：不只換顏色字型。至少一個方向是第一屏資訊最少的版本（只留「一直在」那一層）。
5. **亮點讓畫面變少或變清楚**：只是多加一塊的不算。
6. **符合使用情境**：對照第 1 步問到的「多久用一次、用多久」。每天長時間使用的工具，大面積高彩度色塊與強對比不放在一直看得到的地方（頂列、固定列、整片背景），亮點放在資訊安排、排版或小面積的記號上；行銷頁、偶爾才開的頁面不受此限。使用者要求大膽的方向時，大膽放在資訊安排、字與版面。
7. **換題測試**三題（distinctive-design.md）。
8. **圖示**：工具型介面的頂列與主要操作有圖示加文字標籤；沒有的話寫明理由（ux-patterns.md〈圖示〉）。
9. **UX 四項**：NN/g 啟發式的 2 用詞、4 一致、6 辨識勝於回憶、8 極簡，靜態畫面就看得出來，現在看；其餘在第 8 步看完整流程。
10. **工具檢查**：`contrast.py` 全過；`screenshot.mjs` 結束碼 0（沒有腳本錯誤、頁面真的畫出來）。

## 方向稿說明的欄位

每個方向一段，欄位固定，方便比較：

- 概念（一句話，講畫面怎麼安排）
- 資訊安排：第一屏有什麼、什麼收在哪；和其他方向差在哪
- 第一眼測試的那一句話
- 第一屏可操作元素數（桌機／手機；原型的數字）
- 使用情境：多久用一次、用多久；常駐區域用了哪些顏色與面積
- 色彩與字型、依據
- 圖示：哪一套、放在哪些地方、哪些是純圖示按鈕
- 亮點：是什麼、取代了什麼
- 換題測試三題的答案
- 已知代價（例：收進抽屜後常用者多按一下）

## 自我退件規則

沒有人退件、要自己迭代時：

- 每輪先問「可以拿掉或合併什麼」，再問「缺什麼」。每輪至少拿掉或合併一樣；只加不減的一輪不算一輪。新加的東西取代了原本的元素（例：狀態記號兼作圖例，取代另外的圖例區），算拿掉或合併。
- 每輪重做第一眼測試與第一屏元素數並記下來。數字上升時寫出原因：是第一屏看得到更多主要內容就沒問題，是控制項變多代表方向錯了。
- 不用「哪裡還不夠有特色」當唯一的問題，它只會讓每一輪都在加東西。

## 使用者全權委託時

使用者明說「全部你決定、不要停下來問我」才算；只對某一題說「你決定」不算。這時檢查點不能直接跳過，也不能由做設計的同一個 context 自審，改用下表的替代做法。

| 檢查點 | 替代做法 |
|---|---|
| ① 收素材 | 從需求、原型與一手資料自己定；每個假設列進報告的「請確認」 |
| ② 分層表 | 自己定，併入第一次獨立審查（審查者看方向稿時會指出第一屏太多） |
| ③ 選方向 | **獨立審查一**：所有方向的截圖 |
| ④ 退件 | 照〈自我退件規則〉；定稿前做**獨立審查二**：選定方向的截圖。沒通過、改完後可做**獨立審查三**，這是最後一次 |
| ⑤ 定案 | 寫完 DESIGN-SYSTEM.md 後照使用者指定的範圍展開；報告開頭列出「待你推翻的決定」 |

獨立審查的做法：

- 用 Agent 工具開一個**全新 context** 的 subagent（不是 fork，fork 會帶著你的理由）。
- 只給它：截圖檔路徑（第一屏圖與整頁圖）、使用者的原始需求原文、功能清單（只列這個畫面該有的功能名稱，不列分在哪一層）；有原型時加原型同一頁的截圖當對照。
- 收起來的東西也要給它看：主要的抽屜、選單、收合列各截一張打開後的第一屏圖。方向稿讓網址參數決定預設打開哪一個（例 `index.html?open=history`，頁面載入時讀參數打開），再用 `screenshot.mjs` 截。只給關著的畫面，審查者會把收起來的功能都記成找不到。
- 不給：概念、設計說明、選擇理由、你偏好哪個。截圖檔名與資料夾用中性名稱（`a`、`b`、`c`），不要讓方向名洩漏概念。
- 審查者的第一眼答案和你自己寫的第一眼測試不一致，那個方向不合格，要改。
- 換題看審查者在第 4 題逐條列出的版面決定：一條都列不出來，這個方向不合格，改掉或換方向；列得出來，被指認為某個現成風格時只是表面元素像，把那些元素拿掉或減弱即可，不必放棄方向。看列出的理由，不看它一句「要改／不用改」的結論。不能用「這是刻意的」「它從題材來」過關。
- **只有方向層級的問題算不通過**：第一眼答案不一致、換題一條都列不出來、功能找不到也看不出入口。其餘意見（字太淡、位置、文案）是修改清單，改完或寫明不採納的理由即可，不擋定稿。
- 每條意見記「採納／不採納」。不採納要有畫面上或需求裡的依據。
- 審查者選的方向和你不同時，可以不照它選，但要把雙方理由都寫進報告。
- 報告要有「獨立審查」一節：審查者看了哪些圖、原話重點、每條意見的處理。使用者指定了報告格式時照他的格式，「待你推翻的決定」與「請確認」兩張表放在開頭。
- 審查最多三次（選方向一次、定稿前兩次）。第三次仍不通過就停手，不再為了通過而一直改：報告的結論寫明「獨立審查沒有通過」，列出沒解決的意見、各自的取捨，交給使用者決定。
- 沒有 Agent 工具、開不了 subagent 時，在報告寫明「沒有做獨立審查」，不能寫成自審通過。

審查者是 AI 不是使用者，它擋得住明顯的套路與混亂，擋不住「使用者就是不喜歡」。所以報告仍要把選擇與代價攤開，方便使用者回來推翻。

## 審查者的提示

照這個內容給，括號處換成實際路徑與文字；不要加任何設計說明：

```
你是第一次看到這些畫面的人。下面是使用者的原始需求，以及幾張介面截圖。
請只根據截圖回答，不要推測設計者的意圖；用 Read 逐張看圖。

原始需求：
<使用者的原文>

功能清單：
<功能名稱，一行一個>

截圖：<路徑清單，註明哪幾張是同一個方向的桌機／手機、第一屏圖或整頁圖、哪幾張是抽屜或選單打開後的畫面、哪一張是原型>
固定在畫面上下的列在整頁圖裡會出現在中間、蓋住內容，那是截圖方式造成的；這些列的位置以第一屏圖為準。

對每個方向分別回答：
1. 第一眼看到什麼？要開始工作，第一步會按哪裡？有沒有讓你猶豫的地方？
2. 這個畫面像不像 AI 常產出的設計？像哪一種現成風格？依據是畫面上的哪些元素？
3. 哪些東西拿掉也不影響完成主要任務？逐項列出。功能清單裡哪些項目在畫面上找不到，也看不出入口在哪？（收在抽屜或選單裡、入口看得到且寫明內容的，不算找不到。）
4. 把題目換成銀行：逐條列出版面結構（什麼放在哪、怎麼排）裡，哪些決定換成銀行會不合理，每條說明為什麼只適合原本的題目；一條都沒有就寫「沒有」。表面（顏色、文字、圖樣）要改的另外列，不算在內。
5. 圖示：頂列與主要操作有沒有圖示？有沒有看不懂、旁邊也沒有文字說明它是什麼的圖示？
6. 照需求描述的使用頻率與時間用這個畫面，哪裡會累或干擾？依據是畫面上的哪些元素？
最後：這些方向裡，哪一個最適合需求描述的使用情境？都不適合就直說，並說明缺什麼。
```
